# 観測基盤の設計

> 対象ピックアップは、観測できないものを拾えない。
> [PICKUP-MECHANISM.md](PICKUP-MECHANISM.md) が「取れた後にどう選別するか」なのに対し、
> 本書は「そもそも何をどう取るか」を決める。

## 1. 二択と、その本当のトレードオフ

業界には2つの流派があり、**どちらも重大な欠落を抱えている**。

| | プロセスマイニング（API / イベントログ） | タスクマイニング（デスクトップ記録） |
|---|---|---|
| 見るもの | 基幹システムが記録したイベント | 画面上の操作（キー・クリック・遷移） |
| 強み | 非侵襲・継続的・同意の壁が低い | **システムとシステムの隙間**が見える |
| 致命的な欠落 | 「システムが記録したものしか捉えられない。企業アプリの外で起きている作業は結果が不完全なまま」 | 同意プログラムが要る。かつ**調査型**で、「記録した人・対象アプリ・回した週」しか映らず、**終わった瞬間から陳腐化する** |

タスクマイニングが存在する理由は、ログマイニングがデスクトップに残す死角そのものである。
逆にタスクマイニングは、一度きりの調査で終わり、以後の変化が見えない。

## 2. Litron Builder の選択 — API のみで始める

**デスクトップ記録はしない。APIとWebhookのイベントだけで始める。**
死角があることを認めた上で、死角を画面に出す。

理由は3つ。3番目が本質。

### 2.1 同意の壁が導入を殺す

デスクトップ操作の記録は、各ベンダが明示的な同意と匿名化を要求している水準の行為。
UiPath は「データ主体への告知は顧客の責任であり、我々には同意を取る技術的手段が無い」と明記している。
**同意プログラムを回せるチームは少ない。** 回せないなら製品は入らない。

### 2.2 調査型では運用に載らない

タスクマイニングは「記録した数週間」のスナップショット。
Litron は**回しながら合格率を測り、割れたら降格させる**設計なので、観測が止まると運用が止まる。
継続的に取れることが、精度より先に要る。

### 2.3 G3 と観測範囲は自然に一致する（本質）

ピックアップの G3 は「**検証手段が定義できないものは候補にしない**」だった。

> **機械で検証できることは、ほぼ機械で観測できる。**
>
> 検証の型は 機械判定 / 突合 / サンプル抽査 / 受領確認 の4つ。
> このうち上位3つは、対象がAPIで読める場所にあることを前提にしている。
> 逆に、APIから一切見えない作業は、その成否も機械で確かめられない。
> つまり **G3 を通る候補は、API観測でほぼ捉えられる。**

デスクトップでしか見えない作業は、たいてい G3 で落ちる。
**落ちるものを高い代償を払って観測しても、候補は増えない。**
これが「API のみで始める」を妥協ではなく設計として選ぶ理由。

> ただしこれは仮説である。実データで「G3を通るのにAPIで見えなかった候補」が
> 一定数出るなら、この判断は覆る。そのときに初めてデスクトップ観測を検討する。

## 3. 観測の3層

```
L1 イベント層   誰が・いつ・何に対して何をしたか（API / Webhook / 監査ログ）
L2 成果物層     作られた・変えられたものの中身（差分・本文・添付）
L3 文脈層       L1のイベント列を時間窓で束ねて「一続きの作業」にする
```

ピックアップが使うのは主に **L3**。L1 単体では「PRを見た」「ページを更新した」しか分からず、
それが**一続きの仕事**だったかは分からない。束ねて初めて「型」の候補になる。

### 各層で取るもの

| ツール | L1 で取れるもの | L2 で取れるもの | 備考 |
|---|---|---|---|
| GitHub | PR / Issue / コミット / レビュー / タグ | 差分・本文 | Webhook で準リアルタイム |
| Notion | ページ作成・更新・移動 | ブロック差分 | 監査ログは 2026-08-09 以降のイベントから |
| Slack | メッセージ・チャネル操作 | 本文（Botが居るチャネルのみ） | **監査ログAPIは Enterprise プラン限定**（`auditlogs:read`） |
| カレンダー | 予定・参加者・時間 | タイトル・説明 | 会議の前後が作業境界になりやすい |
| Linear / Jira | 課題の状態遷移・担当変更 | 本文・コメント | 状態遷移は主経路の骨格になる |

**Slack は Enterprise でないと監査ログが引けない。**
非Enterpriseでは「Botが参加しているチャネルのイベントのみ」に縮退する。
この縮退は画面に出す。取れているつもりで取れていないのが一番悪い。

## 4. セッション化 — イベント列を「一続きの作業」にする

L1 の生イベントを、次の規則で束ねて**作業セッション**にする。

```
1. 同一人物のイベントを時系列に並べる
2. 隣接イベントの間隔が 閾値T（既定 15分）以内なら同じセッションに入れる
3. 対象が連鎖している（PR → そのPRに言及したページ → そのページを貼ったメッセージ）
   場合は、間隔が T を超えていても同じセッションに繋ぐ
4. セッションに含まれるツールの並び順を「経路」とする
5. 経路が一致するセッション同士を束ねて、候補の母集団にする
```

例外率（G2）は、この母集団の中で**主経路から外れたセッションの割合**として出る。
つまり G2 はセッション化の副産物であって、別途の推定ではない。

### 閾値 T の扱い

T=15分 は仮置き。**セッション境界は結果を大きく左右する**ので、
実データで「1つの作業が分断される率」と「無関係な作業が混ざる率」を見て調整する。
この2つはトレードオフなので、片方だけ最適化しない。

## 5. 見えていない範囲を、見せる

L1 にイベントが無い時間帯は、**人が画面で何かしていた可能性がある区間**。
ここを「空白」として扱わず、**「見えていない時間」として明示する**。

- 中身は推定しない。「何をしていたか」を勝手に書かない
- 量だけ出す。「今週、観測できなかった作業時間: 約11時間」
- 空白が大きいツール（例: ローカルのExcel作業）は、名指しで「ここは見えていません」と出す

**見えていない範囲を隠すと、候補一覧が「これで全部」に見えてしまう。**
それが一番危険な誤解なので、常に併記する。

## 6. 保持と破棄

| 層 | 保持 | 理由 |
|---|---|---|
| L1 イベント | 90日 | 例外率の母集団に要る。それ以上は精度に効かない |
| L2 成果物 | **候補化したら破棄** | 要件化に使ったら用済み。本文を溜める必要が無い |
| L3 セッション要約 | 型が生きている限り | 降格判断の基準線になる |

生ログを溜め続けない。**溜めた瞬間に、溜めたこと自体が説明責任の対象になる。**

## 7. 未解決

- **閾値 T（セッション境界）と例外率の閾値（10% / 40%）は、どちらも実データ待ち。**
  現状は仮置きで、根拠はまだ無い
- **複数人にまたがる作業**（誰かが起票し、別の誰かが処理する）のセッション化は未設計。
  本書は単一人物の連鎖しか扱っていない
- **Slack 非Enterprise での縮退**が、実際どこまで候補を減らすかは未計測
