# 対象ピックアップの仕組み

> 「汎用エージェントの対象ピックアップの仕組み化」の設計。
> これが Litron Builder の中心機能。

## 1. 素朴な設計はなぜ失敗するか

素朴な設計はこうなる。

```
行動ログ → 反復を検知 → 「7回やってますね、自動化しませんか」
```

これは task mining が既にやっていることで、**そして失敗が知られている**。

RPA の候補選定の定石は「例外がほとんど無い、予測可能でルールベースな処理を探せ」。
逆に言えば、**反復しているように見えて例外を含む作業を拾うと、自動化は壊れる**。
UIが少し変わっただけで止まる。想定外の入力で落ちる。
「RPAは死んだ」と言われた原因はほぼこれである。

つまり **頻度は判定軸として弱い**。7回やったという事実は、
その7回が同じ経路だったかどうかを何も言っていない。

## 2. 4つのゲート

ピックアップは4つのゲートを順に通す。**通過ではなく、通り方で扱いが変わる。**

### G1 反復性 — どれだけ繰り返しているか

観測期間内の実行回数と、1回あたりの所要時間の推定。
`頻度 × 所要時間 = 回収可能時間`。これは「やる価値」の目安であって、**合否ではない**。

### G2 ばらつき — 何回が同じ経路だったか

観測した N 回のうち、主経路から外れた回数を数える。`例外率 = 外れた回数 / N`。

ここが本設計の肝。**例外率が高い＝不採用、にしない。**
RPA は不採用にするしかなかった。エージェントは判断ができるので、
**例外率で「モード」を割り当てる**。

| 例外率 | モード | 意味 | 例 |
|---|---|---|---|
| 〜10% | **決定論** | 手順を固定して回す。安い・速い・壊れたら分かる | 定型レポートの生成、ファイル整理、定期集計 |
| 10〜40% | **エージェント** | 判断を委ねる。ただし検証が必須 | 問い合わせの一次振り分け、差分レビューの指摘反映 |
| 40%〜 | **下書き** | エージェントは下書きまで。人が仕上げる | 議事録、メール下書き、日報 |

> **現状の Push 型（議事録・メール下書き）は、この表の一番下だけをやっている状態。**
> 拡張の方向は「もっと下書きを増やす」ではなく、
> **例外率の低い側へ登っていくこと**。同じ仕組みで、上2段が取れる。

### G3 検証可能性 — 何をもって「できた」とするか

**このゲートを通らないものは、どれだけ反復していても候補にしない。**

検証手段が定義できない作業を自動化すると、「やったが、できていない」状態が
静かに積み上がる。Anthropic が検証ループを最重要と言っているのと同じ理由。

検証手段の型は4つ。

| 型 | 例 |
|---|---|
| **機械判定** | スキーマ検証、件数一致、テスト通過、差分ゼロ |
| **突合** | 元データと出力の照合、二重計算の一致 |
| **サンプル抽査** | N件中k件を人が見る。合格率が閾値を下回ったらモードを落とす |
| **受領確認** | 送り先が受け取った／返信した、という事後シグナル |

どれも定義できないなら、候補から落とす。落とした理由も記録して見せる。

### G4 可逆性 — 戻せるか

Claude Code の reversibility-weighted risk をそのまま採る。
**「危険か」ではなく「戻せるか」で分ける。**

| 区分 | 扱い |
|---|---|
| 戻せる（下書き保存、内部ファイル生成） | 自動で適用してよい |
| 戻せるが影響が外に出る（社内共有、チケット更新） | 適用するが通知して、取り消し導線を常設 |
| 戻せない（外部送信、公開、決済、削除） | **必ず人の決裁を挟む。例外なし** |

## 3. 候補スコア

4ゲートを1つの数字に潰さない。**潰すと「なぜ選ばれたか」が説明できなくなる。**
4軸をそのまま持ち、並べ替えだけにスコアを使う。

```
回収可能時間 = 頻度 × 所要時間        … どれだけ得か
確度        = 1 − 例外率              … どれだけ安定か
検証強度    = 機械判定 > 突合 > 抽査 > 受領確認
決裁負荷    = 不可逆ステップ数        … どれだけ人を呼ぶか

並べ替え順 = 回収可能時間 × 確度 × 検証強度 ÷ (1 + 決裁負荷)
```

UI では**この4軸を常に並べて出す**。合成スコアだけを見せない。

## 4. 観測とプライバシー

task mining はデスクトップ操作を記録する手法で、
**明示的な同意と匿名化が前提**だと各ベンダのドキュメントが明記している。
UiPath は「データ主体への告知は顧客の責任であり、我々には同意を取る技術的手段が無い」
とまで書いている。

Litron Builder はここを製品仕様として先に決める。

- **観測範囲は本人が選ぶ。** 既定は「オフ」。接続したツール単位で個別にオンにする
- **観測しているものを常に見せる。** 何を、いつから、どれだけ溜めたかを画面に出す
- **生ログは候補化したら捨てる。** 残すのは「型」と根拠の要約のみ、保持期間つき
- **他人の画面は観測しない。** チーム機能は本人が公開した型だけを共有する

これは法務対応ではなく、**受け入れられるかどうかの分かれ目**である。

## 5. 候補から運用までの流れ

```
1. 観測      接続したツールの行動ログを集める（同意した範囲だけ）
2. 束ねる    似た実行をまとめて1つの候補にする
3. 4ゲート   反復性 / ばらつき / 検証可能性 / 可逆性 を測る
4. 要件化    観測した N 回から、入力・出力・例外・検証方法を下書きする
5. 接続      必要な認証とAPIを洗い出し、クリックで繋ぐ
6. 試走      過去の実行に対して空撃ちし、当時の結果と突合する
7. 決裁      人が範囲を確認して委任する（不可逆ステップがあれば必ず）
8. 運用      回しながら例外率と検証合格率を測り続ける
9. 降格      合格率が閾値を割ったらモードを1段下げて人に戻す
```

**9 の降格が無い自動化は運用できない。**
一度任せたら任せっぱなし、が RPA の失敗の後半分だった。

## 6. Pull 型との合流

Pull（自然言語で書く）でも、G3 検証可能性と G4 可逆性は**同じように課す**。

```
「毎週金曜に今週のPRをまとめて、チームのSlackに流して」
    ↓
  検証方法は？   → 対象PR件数と本文中の件数の一致（機械判定）
  不可逆は？     → Slack送信は取り消せない → 決裁を挟む or 下書き止まり
```

自然言語で書けたからといって、検証方法の無い自動化を通さない。
**Push と Pull で下流の厳しさを変えない**。ここが揃っていないと、
「Pull で書けば審査が緩い」という抜け道ができる。
