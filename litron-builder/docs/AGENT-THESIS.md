# エージェントとは何か — そして Litron Builder が何を取るか

> 「Pull型・エージェントとは？を深く考え、Codex、Claude Code がなぜいいのか、
>  いいとこ取りをしてリストアップ」への回答。

## 1. エージェントの定義（一問一答との違い）

エージェントとは、**目標が満たされるまで「文脈収集 → 実行 → 検証」を回し続けるもの**。
一回答えて終わるものはエージェントではない。ループが本体で、モデルは部品。

この定義から外せない要素は3つしかない。

| 要素 | 無いとどうなるか |
|---|---|
| **実行環境に入っていること** | 外からAPIを叩くだけでは、システムとシステムの隙間で起きている手作業に手が届かない |
| **検証手段を持っていること** | 「やった」と「できた」の区別がつかない。壊れたまま回り続ける |
| **止まれること／戻れること** | 不可逆な失敗を一度でも出したら、二度と任せてもらえない |

## 2. Codex / Claude Code がなぜ効いているのか

### 2.1 検証ループが品質を決めている

Anthropic 自身が、**Claude に自分の仕事を検証させる手段を与えることが
「最も重要」で、最終品質がおよそ 2〜3倍変わる**と書いている。
そして「**compiles か works か**」の区別こそが勝負どころだと。

これは自動化全般に効く話で、コードに限らない。
「メールを書いた」と「そのメールが用を成した」は別物である。

### 2.2 ループの形

**文脈収集 → 実行 → 検証** の3相が混ざりながら繰り返される。
一発生成ではなく、観測して軌道修正する。だから仕様が曖昧でも着地する。

### 2.3 安全側の設計思想

Claude Code は4つの原則で組まれている。

1. **deny-first（既定は拒否・確認）**
2. **段階的な信頼（graduated trust）**
3. **多層防御**
4. **可逆性で重み付けしたリスク判定（reversibility-weighted risk）**

4番目が特に効く。「危険かどうか」ではなく「**戻せるかどうか**」で判断を分ける。
戻せる操作は任せ、戻せない操作は人に返す。これは制約ではなく製品価値である。

## 3. Zapier / n8n / Make に無いもの

2026年時点で自然言語からのワークフロー生成自体は既にある
（Zapier Copilot、Make の Maia、n8n の AI ノード群）。
したがって「自然言語でワークフローを組める」だけでは差にならない。

無いのは次の3つ。

- **検証ループが無い。** 組んだら流れるだけ。壊れたら失敗するだけで、直そうとしない
- **AIがアーキテクチャになっていない。** Zapier は AI を「ワークフロー内の一機能」として
  扱っており、実行間の永続的な記憶が無い
- **エージェント基盤として未成熟。** Make のエージェントビルダーはベータで、
  自律的に動くワークフローの実運用には足りていない

## 4. いいとこ取りリスト

### Codex / Claude Code から取るもの

| 取るもの | 理由 |
|---|---|
| **検証ループ** | これが無い自動化は必ず腐る。品質の 2〜3倍がここで決まる |
| **「何を」だけ言えば済むこと** | 手順を人間が書き下す時点で、自動化のコストが便益を超える |
| **途中で止められる／操縦できる** | 長い仕事は必ず途中で前提が変わる |
| **経過が見えること** | 信頼は結果ではなく経過の可視化からしか積み上がらない |
| **deny-first と可逆性による重み付け** | 不可逆操作を人に返すのは、機能の欠落ではなく設計の中心 |
| **実行環境の内側にいること** | 隙間の手作業は、外からのAPIでは観測も実行もできない |

### Zapier / n8n から取るもの

| 取るもの | 理由 |
|---|---|
| **トリガーの豊富さ** | 起点が無ければ Push 型は成立しない |
| **実行の再現性・冪等性** | 毎回違う結果を出す自動化は運用に載らない |
| **実行履歴とリトライ** | エージェントでも失敗する。運用の器は別に要る |
| **認証の使い回し** | 「クリックで繋がる」体験の本体はここ |
| **成果物がワークフローとして残ること** | 会話だけで消えると、チームの資産にならない |

### どちらも持っていないもの — ここを Litron Builder が作る

> **対象の発見。**
> Zapier も Claude Code も「**何を自動化するか**」は人間が持ち込む前提で立っている。
> Claude Code は「このバグを直して」と言われて初めて動き、
> Zapier は「このZapを作る」と決めた人がいて初めて動く。
>
> 「そもそも自分の仕事のどれが自動化できるのか」に答えるものが無い。
> これが **対象ピックアップ** であり、Litron Builder の中心機能である。

## 5. Push と Pull を分けない理由

Push（エージェントが見つける）と Pull（人が自然言語で書く）は、
**別機能ではなく同じものの入口違い**として設計する。

どちらも最終的に同じ一つの物を作る。本書ではこれを **「型」** と呼ぶ。

```
Push  観測ログ ─┐
                ├→ 【型】 → 検証 → 運用 → 振り返り
Pull  自然言語 ─┘
```

型 = 「いつ・何を条件に・何をして・何をもって完了とするか」の束。

- **Push は型を見つける。** 使う人はまだ自動化を考えていない
- **Pull は型を書く。** 使う人はもう自動化したいものを持っている

入口が違うだけで、下流（検証・接続・運用・振り返り）は完全に共通にできる。
**統合UIとはこの合流のこと**であり、画面を2つ並べることではない。
